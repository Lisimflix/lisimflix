# UI-1: M1 Browser Player Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Status:** Draft; unassigned and unimplemented.
**Goal:** Let the M1 viewer sign in, select the configured movie and watch its original stream in the browser.
**Architecture:** A small React application consumes the generated API types and native HTML video. A loopback-only fixture harness supports UI development without the Go server; production uses only same-origin API requests.
**Tech Stack:** The exact React/TypeScript/Vite/Playwright pins in [CTR-1](2026-10-25-ctr-1-m1-contracts.md).
**Spec:** [Design §§5, 6, 9.3](../specs/2026-10-24-lisimflix-design.md). Existing home layouts/themes remain the later library/interface direction; do not redesign them in this player slice.

## Global constraints

- M1 is a complete 1080p SDR H.264 MP4 at original encoded quality, without remux/re-encoding.
- Required final clients: Chrome and Firefox on Linux, Windows and macOS. Browser automation alone does not certify those six real targets.
- Trusted-LAN HTTP works with local username/password; no service worker, public domain, provider account or third-party CDN is required.
- Claim `web/src/main.tsx`, `web/src/player/**`, `web/src/api/client.ts`, `web/tests/**`, `web/playwright.config.ts` and `web/src/styles.css` after the seed. Do not edit schema/generated types, manifests, backend or root deployment files concurrently.
- Start/module dependency: CTR-1. Integration dependency: real runtime and delivery APIs; source fixtures do not prove MOVIE acceptance.

## Review focus

1. Passwords/grants stay out of localStorage, logs and external URLs.
2. Browser autoplay rejection gives a usable Play action instead of an endless spinner.
3. Stale/duplicate requests and unmounts cannot attach a previous session to the player.
4. Heartbeats remain active during a full movie and stop cleanly on logout/end/unmount.
5. Fixture success is clearly separated from live media/authentication evidence.

## Interfaces

Create `web/src/api/client.ts` using generated `components["schemas"]` types. Export `M1Client` and `createClient(baseUrl?: string): M1Client` with:

```ts
interface M1Client {
  session(signal?: AbortSignal): Promise<AuthState>;
  login(username: string, password: string, signal?: AbortSignal): Promise<AuthState>;
  logout(signal?: AbortSignal): Promise<void>;
  movies(signal?: AbortSignal): Promise<Movie[]>;
  start(movieId: string, key: string, signal?: AbortSignal): Promise<PlaybackSession>;
  heartbeat(id: string, sequence: number, signal?: AbortSignal): Promise<void>;
  stop(id: string, signal?: AbortSignal): Promise<void>;
}
```

`createClient` defaults to the page origin; reject cross-origin overrides in production. Fetch includes same-origin credentials; unsafe requests send the last valid session response's CSRF token. Login replaces that token after rotation. Start sends a new idempotency key per deliberate play, retaining it for a retry of that same request. Parse safe API errors and handle non-JSON network failures without exposing raw payloads.

Export `M1App({client}: {client: M1Client})` from `web/src/player/M1App.tsx`. `main.tsx` composes it with `createClient()`. Keep the fixture client out of that production composition. The UI needs a labelled login form, configured movie title/Play action, native video controls, preparation/error/ended states and logout. Do not add library search, metadata, custom themes or persisted progress to M1.
